  Wrote it to hidra/PLAN.md. Summary:

  Verdict: feasible, with one hard constraint. Every link works except
  browser→USB-serial on a tablet:

  - ESP32 as BLE HID — already proven by your existing sketch.
  - Swapping WebSocket for serial input — trivial firmware simplification.
  - The risk: Web Serial is desktop/ChromeOS only. Android support only landed
  in Chrome 148 beta (April 2026) and is Bluetooth-RFCOMM-first, with USB serial
  on a limited device set — not something to build on. The dependable Android
  path is Google's web-serial-polyfill over WebUSB, which Chrome for Android has
  long supported. It works because stock Android kernels carry no CH9102/CP210x
  driver, so WebUSB can claim the interface. Write the app against
  navigator.serial and swap the implementation at runtime.
  - iPad is disqualified as tablet A — no Web Serial, no WebUSB in Safari. If
  that's your intended device, the design has to change (fallback: tablet A
  talks to the stick over Web Bluetooth instead of USB, making the stick
  BLE-central and HID-peripheral).

  Other things the plan designs around: DTR/RTS auto-reset rebooting the ESP32
  when the port opens; boot-log garbage on the same UART; BleKeyboard
  incompatibility with arduino-esp32 core 3.x; PWA needing an HTTPS origin; and
  no arduino-cli on this x86_64 box (builds happen on the Pi).

  The plan also specifies a line-oriented ASCII protocol at 115200 with explicit
  key down/up rather than the example's write()-only approach — that's what
  makes held modifiers, key repeat, and press-and-hold work — plus a release-all
  watchdog so keys can't stick if the browser dies. Then five phases:
  hardware/toolchain truth-check → firmware rewrite → web keyboard on desktop →
  Android/PWA (where the risk lands) → polish.

  Four open questions at the end of the doc; the first one matters most: what is
  tablet A? Its OS determines whether the §2 risk applies at all.

● Feasibility check on UPDATE_1 is written up as Appendix A in hidra/PLAN.md,
  plus a concrete test page at src/web/captest.html.

  Q1 — Can the ESP32 run a BLE control server and BLE HID together, with both 
  tablets connected? Yes. It's one peripheral with one GATT database holding two
  services; both tablets connect as centrals. The controller supports up to 9
  concurrent connections (Espressif recommends ≤3); we need 2. Three things make
  or break it:

  - Advertising must be restarted in onConnect — BLE stops advertising on
  connection, so without this the second tablet can never discover the device.
  This is the classic failure of this design.
  - Mixed security per connection: tablet B bonds/encrypts for HOGP, while
  tablet A's control service stays unauthenticated, because Web Bluetooth can't
  drive a pairing dialog. That's legal — BLE security is per-connection.
  - 31-byte advertising limit: HID + appearance in the ADV packet, the 128-bit
  control UUID in the scan response.

  Two findings worth your attention. Web Bluetooth blocklists the HID service 
  (0x1812) outright — a page can never touch it, so tablet A must go through a
  custom Nordic-UART-style service. Fine here, but it kills any simpler variant.
  And tablet A must never bond with the stick in system Bluetooth settings —
  Android would claim it as a real keyboard and tablet A would start receiving
  its own keystrokes.

  Cost: BleKeyboard assumes it owns the server and advertising, so this likely
  means porting to NimBLE-Arduino. The §4 line protocol and parser carry over
  unchanged, though — only the byte source changes.

  I'd recommend Architecture B, mainly because it sidesteps the WebUSB
  interface-claim gamble that was the plan's biggest unknown. The real cost is
  power: no cable means the stick lives on its ~120 mAh battery.

  Q2 — Amazon Fire as tablet A? Probably, but it needs measuring. Fire OS is
  Android-derived and Silk is Chromium-based, but Amazon documents no Web
  Bluetooth/WebUSB/Web Serial support in Silk — assume off until tested.
  Sideloading Chrome isn't a clean escape (it needs Play Services installed
  first, and that breaks on Fire OS updates); a GMS-independent Chromium like
  Cromite is lower-friction. The hardware is fine either way — modern Fire HDs
  have BLE and do support USB OTG — so the browser, not the tablet, is the
  constraint on both architectures.

  src/web/captest.html settles it: host it on any HTTPS origin, open it on the
  Fire tablet in Silk, and it prints the capability table and opens each
  chooser. The USB button dumps VID/PID and attempts claimInterface on every
  interface, which answers the Architecture A question at the same time. Fifteen
  minutes with the real hardware resolves both questions — send me the log and
  I'll lock the architecture.

  report, so held modifiers, key repeat, press-and-hold, and 6-key rollover all
  work. Usages 0xE0–0xE7 maintain the modifier bitmask themselves, so the client
  sends modifiers as ordinary key events.

  WebSocket frames are split into lines and pushed onto a FreeRTOS queue; loop()
  drains it. No BLE calls happen on the AsyncTCP task — that task has a small
  stack and BLE work there is a known way to get mysterious crashes. It also
  fixes a race in the original sketch, which had a single shared scrollText
  buffer written from the async callback.

  The watchdog releases everything after 3 s of client silence, and a WS
  disconnect enqueues an R immediately — otherwise a dropped connection leaves
  tablet B with a stuck modifier and an infinite key repeat. The page pings
  every 1.5 s to feed it.

  Passphrase is generated from an unambiguous alphabet (no 0/O/1/l/I — you're
  reading it off a 135 px screen), stored in NVS, shown as text plus a
  WIFI:S:…;T:WPA;P:…;; QR for camera join. Button A cycles join-QR / URL-QR /
  status; holding B for 1.5 s regenerates and reboots.

  Connectivity probes (/generate_204) answer 204 so Fire OS doesn't nag or drop
  the network, while DNS hijacks every hostname and onNotFound serves the
  keyboard — so any URL typed lands on it.

  One thing to confirm on the Pi: pin the ESP32 core to 2.x. ESP32-BLE-Keyboard
  doesn't build against core 3.x without a NimBLE fork — and if you later do
  Phase 3, that same fork is what you'd move to anyway.

  Polish, in rough order of how much you'd feel it. Real-use ergonomics come

  when tablet A sleeps, which the soak test would surface. Then the smaller
  things from §5: layout config, macros, LCD niceties.

  Phase 3 (BLE transport) buys tablet A its internet back and much better
  battery life. Cheaper than originally estimated — the build already links
  NimBLE — but it still has that one unproven step: whether Silk can reach GATT
  while the stick is advertising HOGP and bonded to tablet B. Worth doing only
  if the WiFi-only tradeoff or the charging cable actually bothers you in daily
  use.

  The soak test I suggested earlier is still the highest information-per-minute
  thing available: battery life under SoftAP, link survival across tablet sleep,
  and whether keystrokes still land after an idle hour.

  My suggestion: use it for a few days first. Real annoyances will tell you
  which of these is worth doing better than any list I can write now.
