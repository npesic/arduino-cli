● Plan written to android/PLAN.md. The headline:

  Feasibility: green, but the brief has one wrong premise. Android can be a HID
  keyboard for another device — BluetoothHidDevice (API 28+, works on Pixels)
  lets an app register a HID report descriptor and push reports. But that's
  classic Bluetooth HID, not BLE/HOGP. A normal app cannot expose HOGP: AOSP's
  GATT server treats HID service UUID 0x1812 as restricted and rejects
  addService() without the privileged system permission. Functionally it makes
  no difference — tablet B still sees an ordinary Bluetooth keyboard — but "over
  BLE" is inaccurate for the Android build. High confidence on both points,
  unverified on your hardware; that's what Phase 0 exists to settle.

  The ESP32 disappears entirely. No AP, no passphrase, no QR codes, no page.h
  build step, no flash budget. The phone talks straight to tablet B.

  Most of the PWA survives. keymap.js verbatim (HID usage ids are exactly what
  sendReport wants), style.css verbatim, app.js minus the transport. Only
  transport.js and the wire protocol die — there's no wire anymore, D 4 0
  becomes a direct call in-process. The firmware's 6KRO model is already the
  boot-keyboard descriptor, 1:1.

  For appearance fidelity I recommend hosting src/web/ in a WebView rather than
  rewriting in Compose — swap transport.js for a @JavascriptInterface bridge and
  it doesn't just resemble the PWA, it is the PWA, for about twenty lines of
  glue. A native Compose layout is Phase 4, and because the transport sits
  behind an interface, that's a UI swap and nothing more.

  Phases: 0 = spike (one button, one letter, prove it lands on the Fire HD 10),
  1 = transport + report builder, 2 = the keyboard UI, 3 = Android polish, 4 =
  optional. 0–2 is the working product.

  Two gotchas I'd flag now rather than at demo time: Pixel gesture navigation
  will swallow the edge keys (needs setSystemGestureExclusionRects), and
  reconnect-after-screen-off is the known sore spot for HID-device apps — Phase
  0 characterises it deliberately.

  Open questions are in §6; the ones that actually change the work are which
  Pixel/Android version, and whether the phone must stay usable while connected
  (foreground service) or full-screen-or-nothing is fine for v1. I'd start
  full-screen.

  What exists now, in android/spike/:

  - HidKeyboard.kt — the actual hypothesis. Gets the HID_DEVICE proxy, registers
  an SDP record with a HID 1.11 boot-keyboard descriptor, and pushes 8-byte
  reports. Usages 0xE0–0xE7 fold into the modifier byte and non-modifiers take
  one of six slots — the same rule the ESP32 firmware uses, so keymap.js's
  numbers already work against it. Shaped as the HidTransport Phase 1 needs, so
  it outlives the spike even though the UI won't.
  - HogpProbe.kt — I decided the plan shouldn't just assert that BLE/HOGP is
  closed to normal apps. This tries addService(0x1812) on a GATT server and logs
  the rejection. Cheap insurance: if it ever succeeds, the architecture changes
  and you'll know immediately.
  - MainActivity.kt — throwaway buttons and a timestamped log (long-press to
  copy).

  Toolchain: none of it was installed, so I set up ~/android-sdk (SDK 35,
  build-tools 35.0.0, platform-tools) and ~/gradle-8.9, plus a Gradle wrapper in
  the project. ./gradlew assembleDebug →
  app/build/outputs/apk/debug/app-debug.apk, 2.4 MB, debug-signed. Zero
  dependencies — framework views, platform Bluetooth,
  Activity.requestPermissions. Nothing to go wrong except the thing being
  tested. Verified the merged manifest carries BLUETOOTH_CONNECT with the
  neverForLocation flag, so no location prompt.

  To run it:

  cd android/spike
  adb install -r app/build/outputs/apk/debug/app-debug.apk

  Then follow the protocol in spike/README.md — T0 through T5, buttons numbered

  Two things I'd flag about what you'll find. T1 is the kill switch: if

❯ What is the bluetooth handle for tablet to pair with?                         

● Tablet B will see the phone's own Bluetooth name — whatever the Pixel is
  called in Settings → About phone → Device name (typically "Pixel 8" or
  similar). Not "HIDRA".

  The "HIDRA" strings in HidKeyboard.kt:79-85 are the SDP record's service name
  and provider fields. Most hosts, Fire OS included, don't surface those in the
  pairing chooser — they show the adapter name, which the app doesn't set.

  To find it without touching the phone's UI:

  adb shell settings get secure bluetooth_name

  So in T2 you're scanning for the phone's normal name. Whether Fire OS also
  tags it with a keyboard icon or an "input device" label depends on the
  class-of-device bits the stack derives once the HID role is registered —
  that's one of the things the T2 notes field is asking you to record, because I
  don't want to guess at Fire OS's chooser behaviour.

  If you'd rather it announce itself as "HIDRA" to match the ESP32 build, that's
  BluetoothAdapter.setName() — one line, but it renames the whole phone
  globally and persists after the app exits, so it would need saving and
  restoring around the session. Worth doing for Phase 1 if you like the
  branding; I'd leave the spike alone so pairing behaves as ordinarily as
  possible.

  the far side. The underlying value comes from a system property read at stack
  startup. Nothing a sideloaded or Play Store app can touch.

  chrome://bluetooth-internals/#/devices and scan with HIDRA discoverable. That

  What changed: HogpTransport : KeyTransport is the transport MainActivity uses.
  It reuses the same unit-tested ReportBuilder, so the bytes on the wire are
  identical to the classic path — only the carrier differs. HidTransport stays

● Phase 2 is done. The app is now the PWA keyboard, typing over BLE.

  The keyboard is not a fork. index.html, style.css, keymap.js and app.js are
  copied out of src/web/ at build time by a Gradle task — the same files the
  ESP32 serves. I verified this rather than assuming it: appended a marker to
  src/web/app.js, rebuilt, found it in the APK, reverted, confirmed src/web/ is
  clean and back in sync. Edit the layout once, both products get it.

  Only transport.js is Android's own. It declares the same WebSocketTransport
  class name app.js constructs and bridges to KeyTransport instead of opening a
  socket, so it shadows the web one by simply not being copied over. app.js is
  byte-identical in the APK and in page.h — it never learns which host it's on.

  One thing that needed solving. app.js treats an empty location.host as "no
  device, render a preview" — correct when you open the page from disk, fatal
  here, since file:///android_asset/ has no host and the keyboard would have
  rendered dead. So the page is served from a synthetic https://hidra.local/
  origin via a request interceptor that answers from assets. Nothing touches the
  network.

  Two Android-only touches, both in assets/transport.js so src/web/ stays
  host-agnostic: the offline veil reads waiting for a device rather than
  reconnecting, and the function row folds away on short screens with a toggle
  in the status bar. That second one is the sizing problem from §6 — a full
  15-column layout plus function row on the Pixel 2 XL gives roughly 7 mm keys,
  and hiding the row buys the remaining rows their height back. It defaults to
  hidden under 450 CSS px of viewport height.

  Landscape lock, keep-screen-on and immersive mode came along early. They're
  nominally Phase 3, but without them this isn't testable as a keyboard.
  Rotation no longer tears down the WebView either — it would have dropped the
  link mid-sentence.

  and the four shared ones byte-identical to src/web/. One build failure along

  NoActionBar.

  Not run on hardware; still no device here. When you install it, the thing I'd
  watch is key latency and multi-touch chords — shift+letter with two fingers is
  the case where a WebView could disappoint versus native, and it's the one
  that would argue for the Compose rewrite in Phase 4.
