# HIDRA Phase 0 — feasibility spike

One screen, eleven buttons, no keyboard layout. It exists to answer the five unknowns in
[`../PLAN.md`](../PLAN.md) §2 and then be deleted.

**The question:** can a Pixel register as a Bluetooth HID keyboard and type into the Fire HD 10?

Everything else — the layout, the latching modifiers, the WebView — waits until a letter has
appeared on tablet B.

## What is in here

| File | Role |
|---|---|
| `HidKeyboard.kt` | the whole hypothesis: HID_DEVICE proxy, SDP registration, 8-byte reports |
| `HogpProbe.kt` | proves the BLE/HOGP route is closed (PLAN.md §1) rather than just asserting it |
| `MainActivity.kt` | throwaway UI — buttons and a log |

`HidKeyboard` is deliberately shaped like the `HidTransport` Phase 1 needs, so it survives even
though the UI does not. The report descriptor is the HID 1.11 boot keyboard, which is the same
report the ESP32 firmware already sends — tablet B will see a keyboard it has met before.

## Build

The toolchain is installed at `~/android-sdk` (SDK 35, build-tools 35.0.0, platform-tools) with
Gradle 8.9 at `~/gradle-8.9`. `local.properties` points at the SDK and is gitignored, so on a
fresh clone recreate it:

```bash
echo "sdk.dir=$HOME/android-sdk" > local.properties
./gradlew assembleDebug
```

APK lands at `app/build/outputs/apk/debug/app-debug.apk` (~2.4 MB, debug-signed).

## Install

```bash
export PATH=$HOME/android-sdk/platform-tools:$PATH
adb install -r app/build/outputs/apk/debug/app-debug.apk
adb logcat -s HIDRA:*          # optional; the in-app log is the primary record
```

Or copy the APK to the phone and sideload it — nothing here needs adb at runtime.

## Test protocol

Two devices: **the Pixel** (running this app) and **tablet B** (the Fire HD 10, or whatever
should receive the keystrokes). Open a text field on tablet B before starting — a browser
address bar or a notes app.

Long-press the log at any point to copy it. Paste the whole thing into `RESULTS.md`.

### T0 — HOGP is closed (evidence for PLAN.md §1)

Tap **0. probe HOGP**.

*Expect:* `addService(0x1812) failed, status=…`. If it says **SUCCEEDED**, stop and tell me —
BLE HID would be back on the table and the architecture changes.

### T1 — the profile proxy exists (unknown #1)

Tap **1. register**. Grant the Bluetooth permission prompt.

*Expect:* `got HID_DEVICE proxy` → `registerApp() accepted` → `onAppStatusChanged: registered=true`.
*Fail:* `getProfileProxy(HID_DEVICE) returned false` means this Android build has no HID device
role and the whole Android approach dies here — fall back to PLAN.md §2's ESP32-client plan.

### T2 — pairing (unknown #3)

Tap **2. discoverable**, accept the system prompt. On **tablet B**, go to Bluetooth settings,
scan, and pair with the phone.

*Record:* does tablet B offer the phone as a pairable device? Does it describe it as an input
device/keyboard? Does the pairing need a PIN?

### T3 — connect and type (unknown #4)

Tap **3. connect to…**, pick tablet B.

*Expect:* `onConnectionStateChanged: … -> CONNECTED` and the state line turns green.

Then, with a text field focused on tablet B:

| Button | Expected on tablet B | Watch for |
|---|---|---|
| `tap a` | one `a` | latency between tap and character |
| `hold a 3s` | `aaaaaaa…` | repeat is generated by tablet B off the held report |
| `shift+a` | one `A` | modifier byte arrives in the same report as the key |
| `type hidra` | `hidra` | no dropped or reordered characters at 60 ms spacing |
| `release all` | nothing | log shows an all-zero report |

The log prints the raw 8 bytes and the `sendReport` call time in microseconds for every event.

### T4 — survival (unknown #5, the known sore spot)

This is the one most likely to disappoint, so record it carefully.

1. **Phone screen off**, wait 30 s, screen on. Does `tap a` still type? Did the log show a
   disconnect? Did it come back by itself, or did it need **3. connect to…** again?
2. **Tablet B sleeps**, wait 60 s, wake it. Same questions.
3. **Leave the app** (home button), come back. Note that this spike deliberately does *not*
   release keys on pause — Phase 1 will. Does the connection survive?
4. **Walk out of range** ~10 m, come back.

### T5 — latency, roughly

Hold the phone next to tablet B and tap `tap a` a dozen times. Is the character instant,
or is there a visible lag? A rough "feels instant / feels laggy" is enough at this stage;
the `sendReport` microsecond figures in the log only measure the local call, not the air time.

## Exit criteria

Phase 0 passes when **a character typed on the phone appears on tablet B**, and the T4
reconnect behaviour is characterised — working, working-after-a-tap, or broken. Anything else
is Phase 1's problem.
