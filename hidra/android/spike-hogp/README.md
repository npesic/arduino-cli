# HIDRA Phase 0b — HID over GATT (BLE)

**The question:** the Chromebook sees the Pixel during a scan and reads its service list —
including the classic HID UUID `0x1124` — but still filters it out of Bluetooth settings,
because Class of Device and a dozen phone profiles classify it as a phone. Apps cannot change
that. Does advertising as a **BLE** keyboard get past it?

A BLE peripheral is classified from an advertisement this app controls, so `0x1812` goes out in
the advertising data and the host classifies us from that — sidestepping Class of Device rather
than fighting it.

Installs alongside the Phase 0 spike (`com.hidra.hogp` vs `com.hidra.spike`), so both can be on
the phone at once. **Run only one at a time** — they compete for the same Bluetooth stack.

## What is in here

| File | Role |
|---|---|
| `HogpPeripheral.kt` | the GATT server: Device Info + Battery + HID services, and the advertiser |
| `MainActivity.kt` | buttons and a log, same shape as Phase 0 |

The report bytes are identical to the classic build — `[mods, 0, k1..k6]`. Only the carrier
differs. Two HOGP details that are easy to get wrong and are handled explicitly:

- **Services are added one at a time.** Android's GATT server takes one `addService` per
  `onServiceAdded` callback; queueing them wrongly drops services silently and looks exactly
  like a host compatibility problem.
- **The Report Reference descriptor (`0x2908`)** tells the host which report the characteristic
  carries. Without it a host reads the service and ignores it.

## Test protocol

Open a text field on the receiving device first.

### T0b-1 — advertising starts

Tap **1. advertise**. Grant permissions.

*Expect:* `service 0x180A added` → `0x180F` → `0x1812` → `all services registered` →
`advertising 0x1812`.

*Fail:* `peripheral mode unsupported on this phone` means the Pixel 2 XL cannot advertise at
all and Phase 0b dies here. `advertisement too large` means the name/UUID did not fit — the
name is already in the scan response, so this would be a surprise.

### T0b-2 — the Chromebook lists it *(the actual question)*

On the Chromebook: Settings → Bluetooth → Pair new device.

**Does the phone appear now?** This is the entire point of Phase 0b. Note how it is described —
an input device, a keyboard, or something generic.

If it still does not appear, check `chrome://bluetooth-internals` again: if it shows there with
the `0x1812` service but Settings still hides it, ChromeOS is filtering on something other than
what we advertise, and BLE is not the answer either.

### T0b-3 — bonding and subscription

Pair from the Chromebook.

*Expect, in order:* `GATT connected` → reads of `0x2A4B` (report map), `0x2A4A`, `0x2908` →
then the line that matters:

```
*** host SUBSCRIBED to the input report — it is treating us as a keyboard ***
```

That CCCD write is the host committing to us as a keyboard. Everything before it is negotiation;
nothing types without it.

### T0b-4 — typing

Same four as Phase 0, with a text field focused:

| Button | Expected |
|---|---|
| `tap a` | one `a` |
| `hold a 3s` | `aaaaaa…` (repeat generated by the host) |
| `shift+a` | one `A` |
| `type hidra` | `hidra` |

### T0b-5 — the Fire HD 10, for regression

Does the *Fire* also accept the BLE keyboard? If HOGP works on both, HIDRA could use BLE
everywhere and drop the classic path. If BLE works only on the Chromebook, the app needs both
transports and a way to choose — considerably more work, and worth knowing now.

### T0b-6 — reconnect

Screen off 30 s, back on. Does it reconnect by itself? BLE peripherals normally re-advertise on
disconnect; this build does not yet, so a manual **stop** → **advertise** may be needed. Note
which.

## Exit criteria

Phase 0b passes if the Chromebook **lists the phone, bonds, subscribes, and types**. Partial
results are still useful — record exactly how far down the sequence it got, because each stage
failing points somewhere different.
